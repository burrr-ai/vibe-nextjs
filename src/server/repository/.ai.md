# Repository

## 역할

DB 접근의 유일한 창구. api에서 DB를 직접 호출하지 않는다. 반드시 repository를 경유한다.

## 규칙

- 모든 파일에 `import 'server-only'` 필수
- 엔티티는 Aggregate Root 단위로 묶기 (예: post.ts에 comment도 포함)
- 각 엔티티 파일에서 타입도 정의 + export
- 기본 timestamp: `createdAt`, `updatedAt`, `deletedAt`
- 테이블 원본값을 충실히 노출 (프론트 친화적 변환은 api 레이어에서)
- 조회 시 soft-deleted(`deletedAt != null`) 제외가 기본
- 삭제는 무조건 soft delete (`deletedAt` 갱신)

## CRUD 네이밍

| 함수 | 설명 |
|------|------|
| `findAll(filter, pageable: PageRequest): Pageable<T>` | 목록 조회. 두 번째 인자 페이지네이션 필수 |
| `findById(id): T` | 단건 조회 |
| `create(data): T` | 생성 |
| `update(id, data): T` | 수정 |
| `delete(id): void` | soft delete |

## 공용 타입

`repository/types.ts`에 정의:

```typescript
export type PageRequest = {
  page: number
  limit: number
}

export type Pageable<T> = {
  items: T[]
  total: number
  page: number
  limit: number
  totalPages: number
}
```

## 구조

```
repository/
  .ai.md
  types.ts              ← Pageable, PageRequest 등 공용 타입
  schema.dbml           ← 엔티티 관계 설계 (가장 먼저 작성)
  _data/                ← mock 데이터 (server-only)
    {entity}.ts
  {entity}.ts           ← 엔티티 CRUD (server-only)
```

## 작업 순서

1. **`schema.dbml` 먼저 작성** — 엔티티 관계와 필드를 먼저 설계하여 생각을 정리한다
2. `_data/{entity}.ts` 작성 — dbml 기반으로 정규화된 mock 데이터
3. `{entity}.ts` 작성 — CRUD 구현, `_data` 참조

## schema.dbml

- 엔티티 추가/변경 시 반드시 dbml을 먼저 갱신한다
- 관계(1:N, M:N 등)를 명시한다
- auth 스킬이 생성할 테이블은 주석으로 미리 기재되어 있다

## Mock 데이터 규칙 (_data/)

- `import 'server-only'` 필수
- **정규화**: 테이블처럼 flat하게 저장. 중복 없이 ID로 참조
- **관계**: 조인 키를 가진다. `userId`, `postId` 등 FK 필드 포함
- **조회 시 조인**: repository에서 `_data` 간 관계를 맺어서 조회 (실제 DB 조인처럼)
- 하드코딩된 computed 값 금지 — `likeCount` 등은 관련 `_data`에서 계산

## DB 연동 시

mock에서 실제 DB로 전환할 때:
- repository 내부 구현만 `_data` → Drizzle 쿼리로 교체
- 함수 시그니처(인터페이스)는 그대로 유지
- api 레이어는 수정 불필요
