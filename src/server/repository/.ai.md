# Repository

## Role

The single gateway for DB access. The api layer must not call the DB directly — always go through the repository.

## Rules

- Every file must have `import 'server-only'`
- Group entities by Aggregate Root (e.g., put comments inside post.ts)
- Define and export types in each entity file
- Default timestamps: `createdAt`, `updatedAt`, `deletedAt`
- **ID generation uses `uuid()` (UUID v7)** — use the helper in `id.ts`. `Math.random()`, `Date.now().toString()`, and hardcoded IDs are forbidden
- Expose raw table values faithfully (frontend-friendly transforms happen in the api layer)
- Exclude soft-deleted rows (`deletedAt != null`) from queries by default
- Always soft-delete (update `deletedAt`)

## ID Generation

Inside `create()`, the new record's `id` must be generated with `uuid()`. UUID v7 is time-ordered and is safe as a DB PK.

```ts
import 'server-only'
import { uuid } from './id'

export async function create(data: { title: string }): Promise<Post> {
  const now = new Date()
  const post: Post = {
    id: uuid(),
    title: data.title,
    createdAt: now,
    updatedAt: now,
    deletedAt: null,
  }
  posts.push(post)
  return post
}
```

> Pre-baked seeds in `_data/` mock may keep readable strings (`mock-user-001`, etc.). Use `uuid()` only in the runtime `create()`.

## CRUD Naming

| Function | Description |
|----------|-------------|
| `findAll(filter, pageable: PageRequest): Pageable<T>` | List query. Second pagination argument is required |
| `findById(id): T` | Single fetch |
| `create(data): T` | Create |
| `update(id, data): T` | Update |
| `delete(id): void` | Soft delete |

## Shared Types

Defined in `repository/types.ts`:

```typescript
export type PageRequest = {
  page: number
  limit: number
}

export type Pageable<T> = {
  items: T[]
  total: number
  page: number
  limit: number
  totalPages: number
}
```

## Structure

```
repository/
  .ai.md
  types.ts              ← Shared types like Pageable, PageRequest
  schema.dbml           ← Entity relationship design (write first)
  _data/                ← mock data (server-only)
    {entity}.ts
  {entity}.ts           ← Entity CRUD (server-only)
```

## Work Order

1. **Write `schema.dbml` first** — design entity relationships and fields first to organize your thinking
2. Write `_data/{entity}.ts` — normalized mock data based on the dbml
3. Write `{entity}.ts` — implement CRUD, referencing `_data`

## schema.dbml

- Always update the dbml first when adding/changing entities
- Specify relationships (1:N, M:N, etc.)
- Tables that the auth skill will generate are pre-listed as comments

## Mock Data Rules (_data/)

- `import 'server-only'` required
- **Normalized**: store flat, like tables. Reference by ID without duplication
- **Relationships**: hold join keys. Include FK fields like `userId`, `postId`
- **Join at query time**: build relationships between `_data` in the repository when querying (just like real DB joins)
- No hardcoded computed values — derive values like `likeCount` from the related `_data`

## When Migrating to a Real DB

When switching from mock to a real DB:
- Replace only the internal implementation of the repository (`_data` → Drizzle queries)
- Keep the function signatures (interfaces) the same
- The api layer requires no changes
